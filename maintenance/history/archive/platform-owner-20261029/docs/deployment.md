# اتصال و استقرار

به‌روزرسانی قرارداد در ۲۴ اکتبر: ۵۵ سیاست صریح کنترلر از سند جدید در `contracts/platform-permissions.json` همراه برنامه‌اند. `PERMISSION_BINDINGS={}` اکنون این نگاشت مستند را نگه می‌دارد؛ ورودی‌های همین object روی مقدار مستند اولویت دارند و مقدار خالی یک عملیات را غیرفعال می‌کند. نیاز به نگاشت اختصاصی برای عملیات فاقد policy صریح همچنان برقرار است؛ reset مدیریتی MFA حدس زده نمی‌شود. متن‌های قدیمی درباره نبود نگاشت همه عملیات، سابقه قبل از دریافت این قرارداد هستند. مجوز واقعی حساب و تأیید نهایی Backend همیشه لازم‌اند.

برای اجرای محلی آماده، دستورهای [راهنمای Docker](docker.md) را اجرا کنید. این بسته تنظیمات خصوصی مستقل، خروجی standalone، healthcheck و volume پایدار نشست دارد. شرایط امنیت، origin و یک replica در ادامه برای کانتینر هم برقرارند.

## دو مسیر شبکه مستقل

۱. Browser → Next.js باید در استقرار واقعی HTTPS باشد؛ `APP_ORIGIN` را روی origin قطعی و `COOKIE_SECURE=true` بگذارید. cookie نشست HttpOnly و SameSite=Strict است. درخواست تغییردهنده فقط با Origin منطبق پذیرفته می‌شود.

۲. Next.js → Backend فعلی HTTP است. BFF مشکل CORS و Mixed Content مرورگر را حل می‌کند، اما این مسیر را رمزگذاری نمی‌کند. پیش از استقرار نهایی Backend را HTTPS کنید یا مسیر شبکه خصوصی/تونل امن تأییدشده فراهم کنید. tokenها روی HTTP عمومی در معرض مشاهده شبکه‌اند.

## نشست

cookie فقط شناسه تصادفی نشست دارد. access/refresh token با AES-256-GCM در `SESSION_DIRECTORY` ذخیره می‌شوند. کلید ۳۲ بایتی `SESSION_SECRET` باید از secret manager یا محیط امن تأمین شود؛ تعویض کلید نشست‌های قبلی را نامعتبر می‌کند. directory را بیرون webroot با ACL مخصوص service account روی دیسک پایدار قرار دهید. روی Windows به mode یونیکسی اکتفا نکنید؛ ACL واقعی میزبان را تنظیم کنید. فایل‌ها به صورت atomic جایگزین می‌شوند و لاگ شامل token نیست.

نسخه فعلی برای **یک process Node و یک replica** طراحی شده است. قفل هر نشست در process، refresh و تغییر Context را سری می‌کند. سرورهای serverless، cluster و چند replica به store مشترک و قفل توزیع‌شده نیاز دارند؛ با کپی filesystem یا load balancing این شرط برآورده نمی‌شود. پیش از چنین استقراری adapter نشست را به store مشترک معتبر منتقل کنید. فایل نشست منقضی هنگام مراجعه حذف می‌شود؛ پاک‌سازی دوره‌ای فایل‌های قدیمی بر عهده عملیات میزبان است.

## بازیابی و درخواست‌ها

refresh پیش از انقضا و فقط یک بار در 401 انجام می‌شود. خواندن مجاز پس از refresh قابل تکرار است؛ mutation پس از 401 کورکورانه replay نمی‌شود و با پیام تعارض برای بازبینی کاربر برمی‌گردد. تمام درخواست‌ها در یک نشست serial هستند؛ این تصمیم برای صحت تغییر Workspace گرفته شده و توان عملیاتی همزمان همان نشست را محدود می‌کند.

هر درخواست BFF revision زمینه را می‌فرستد. درخواست با revision قدیمی پیش از تماس Backend رد می‌شود. تغییر Workspace با پاسخ معتبر سرور revision تازه ایجاد می‌کند. BroadcastChannel تب‌ها، cancellation و Query Cache را پاک می‌کند؛ Backend همچنان مرجع مجوز است.

`Cache-Control: no-store, private` برای داده API اعمال می‌شود. CDN نباید پاسخ‌های `/api/*` و مسیرهای protected را cache عمومی کند. query key شامل UserId و revision است. enrollment و recovery code در cache Query ذخیره نمی‌شوند.

## پیکربندی مجوز

استثنای آزمون محلی پس از اجازه صریح کاربر: `ALLOW_UNCONFIGURED_OWNER_OTP_TESTING=true` فقط وقتی APP_ORIGIN روی 127.0.0.1، localhost یا ::1 باشد، آزمون OTP را پیش از تنظیم کلید مالک مجاز می‌کند. تأیید کد باعث ورود نمی‌شود: 403 هویت پلتفرم رد و پاسخ مثبت بدون نقش پیکربندی‌شده همچنان مسدود می‌شود. گزینه در origin عمومی اثر ندارد و پیش‌فرض آن false است. برای بهره‌برداری معمول، گزینه را false و کلید واقعی نقش را تنظیم کنید.

ورودی فعلی مختص مالک پلتفرم است. `PLATFORM_OWNER_ROLE_KEYS` باید آرایه‌ای از کلیدهای دقیق و تأییدشده نقش مالک باشد؛ مقدار پیش‌فرض `[]` ورود و درخواست OTP را متوقف می‌کند. نام واقعی از PDF/OpenAPI عمومی قابل استخراج نیست و باید توسط بک‌اند تأیید شود. داشتن نقش تنظیم‌شده بدون `platform.access` نیز کافی نیست. هیچ school role یا نام نمایشی نقش را جایگزین کلید مالک نکنید. هر تغییر این متغیر به راه‌اندازی مجدد process نیاز دارد.

`PERMISSION_BINDINGS` یک object JSON از `METHOD /api/admin/v1/.../{id}` به نام permission واقعی است. نگاشت باید توسط Backend تأیید شود. بدون نگاشت، عملیات fail closed است. هیچ permission از عنوان منو یا الگوی نام حدس زده نشده است. کلیدها به template در OpenAPI اشاره می‌کنند، نه شناسه واقعی رکورد.

از ۲۷ اکتبر ۲۰۲۶، مسیرهای MFA از قرارداد و پنل حذف شده‌اند. ورود با OTP و بررسی نقش واقعی مالک انجام می‌شود؛ تنظیم step-up لازم نیست.

## سایر تنظیمات

فرانت فقط به origin پیکربندی‌شده Backend وصل می‌شود، redirect بالادست را دنبال نمی‌کند و مسیر خصوصی پیام‌ها خارج از allowlist است. responseهای JSON با schema زنده snapshot اعتبارسنجی می‌شوند. تغییر ناسازگار schema به خطای قرارداد منجر می‌شود؛ به داده ساختگی یا تبدیل خطا به صفر منجر نمی‌شود.

CSP پایه، frame denial و nosniff فعال است. سیاست script برای سازگاری Next.js شامل unsafe-inline است؛ unsafe-eval فقط در development فعال می‌شود. پیش از سخت‌سازی CSP با nonce، آن را با حالت build واقعی و زیرساخت مقصد تطبیق دهید. برنامه هیچ analytics یا ارسال خودکار پیام ندارد.
